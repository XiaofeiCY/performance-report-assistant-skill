# Task: Add Output Location Safety Guardrails

## Background

During a manual test, the user opened a random business repository (`E:\work\asi-station-mini`) and invoked the installed `performance-report-assistant` skill from that terminal.

The skill / agent workflow attempted to write git evidence to relative paths such as:

```text
outputs/webapp_commits.md
outputs/mini_commits.md
```

When the `outputs` directory did not exist, the agent created it directly under the current business repository:

```text
E:\work\asi-station-mini\outputs
```

The VS Code source control panel then showed many generated files, including git evidence files and WeCom diagnostic artifacts. This is dangerous because the current terminal directory may be an unrelated product repository. Automatically creating report output folders there can pollute the repository, create accidental commits, conflict with project-owned paths, or confuse users.

## User Need

The user expects the skill to ask where outputs should be saved before creating files.

The skill must not silently create `outputs/`, `wecom_runs/`, git evidence markdown files, screenshots, OCR text files, JSON traces, or final reports inside the current terminal working directory unless the user has explicitly chosen that directory as the output location.

The user also asked why so many diagnostic files were generated even though they were not executing local project files. Clarification: these files are generated by evidence-collection scripts, especially WeCom diagnostic/probe paths, not by the target business repository itself. The skill must make this visible and controllable so users do not feel that every invocation will unexpectedly create a large diagnostic artifact tree.

## Goal

Restore and harden output-location confirmation for all report and evidence collection workflows.

After this task, running the skill from an arbitrary project directory must be safe by default:

- no implicit `mkdir outputs` in the current working directory;
- no relative output paths under a business repo unless explicitly confirmed;
- git evidence can be collected without writing files when output location is not confirmed;
- WeCom diagnostics must use a confirmed output root or an explicit safe diagnostic location;
- diagnostic-heavy modes must be clearly separated from normal report/git evidence modes;
- the user should understand what files will be generated before they are generated.

## Scope

In scope:

- Update `performance-report-assistant/SKILL.md` so output-location confirmation becomes a hard precondition before any file-writing command.
- Clarify that "current workspace `outputs/`" is allowed only after the user confirms the current workspace is the intended report workspace.
- Add a safety rule for arbitrary git repositories: a repository used as evidence is not automatically an output destination.
- Require agents to show planned output paths before running commands that write files.
- For git evidence collection, prefer stdout/no-file mode when the user has not confirmed an output location.
- For WeCom collection/probe/manual modes, require `--screenshot-dir`, `--output`, and `--output-json` paths to be under a confirmed output root before running any mode that writes diagnostics or report files.
- Clarify diagnostic artifact behavior: normal git evidence collection should not create screenshot/OCR/trace directories; WeCom probe/full automation can create many diagnostic files and must warn the user before doing so.
- Add a retention/cleanup expectation for diagnostic outputs: either place them under a confirmed diagnostics folder or tell the user how to remove them after acceptance, without deleting anything automatically.
- Clarify artifact volume and lifecycle so users know whether each skill invocation creates files, which modes create many diagnostics, and how old diagnostics are bounded or cleaned up.
- Update script examples in `SKILL.md` so they do not encourage relative `outputs/...` paths without prior confirmation.
- If needed, add small script-side safety checks or clearer errors to prevent accidental relative output writes from common command paths.
- Sync the fixed skill into the installed Claude skill location if this repository's normal workflow requires that for the user to test the installed skill.

Out of scope:

- Do not change report-writing style, template preservation rules, git statistics logic, clone depth behavior, or all-branch evidence behavior except where required for output safety.
- Do not change WeCom page classification, OCR, template matching, copy strategy, fingerprint verification, desktop input behavior, or keep-awake behavior.
- Do not run full-auto WeCom live automation unless the user again supervises and explicitly authorizes it in the current conversation.
- Do not clean or delete files from `E:\work\asi-station-mini` unless the user explicitly asks for cleanup and confirms the target paths.
- Do not restore `CLAUDE.md` or `AGENT.md`.

## Required Behavior

### 1. Start-of-session output confirmation

Before collecting evidence or generating files, the skill must confirm:

- report type;
- audience;
- period;
- template/reference situation;
- final output location;
- evidence sources.

The existing fast path may still skip already answered questions, but it must not skip output location if any command will write files.

### 2. Evidence repository is not an output folder

If the user provides a local git repository path or starts the agent from a git repository, that repository is evidence input only.

Do not write report artifacts into that repository unless the user explicitly says something equivalent to:

```text
就保存在这个仓库下
可以在当前项目创建 outputs
输出到 E:\work\asi-station-mini\outputs
```

### 3. Safe git statistics mode

If git statistics are needed but no output location has been confirmed:

- run `collect_git_commits.py` without `--output`;
- capture stdout in the agent response/context;
- do not create markdown files yet.

Only pass `--output` after showing the absolute planned path and receiving confirmation or after the user has already provided a clear output folder.

### 4. Safe WeCom diagnostic mode

Any WeCom mode that writes screenshots, OCR files, trace files, markdown, or JSON must use explicit paths under a confirmed output root.

Do not rely on the script's relative default:

```text
outputs/wecom_runs/<run-id>
```

when the current working directory might be an arbitrary project.

### 5. Explain generated files

Before running a writing workflow, the agent should summarize the kinds of files that may appear, for example:

```text
将生成：
- git evidence markdown: ...
- WeCom trace directory: ...（截图、OCR 文本、trace，用于失败诊断）
- final report: ...
```

The user should not be surprised by a large list of screenshots or OCR files in source control.

### 6. Separate normal outputs from diagnostics

The skill must distinguish:

- final report outputs: user-facing markdown, docx, xlsx, pptx, or similar deliverables;
- git evidence outputs: compact commit/statistics text or markdown, preferably stdout until an output path is confirmed;
- WeCom diagnostic outputs: screenshots, OCR text, cropped regions, traces, JSON/JSONL, and probe artifacts.

Normal report generation and git evidence collection should not create WeCom diagnostic folders.

WeCom diagnostic-heavy modes must say plainly that they may generate many files, and those files are for troubleshooting / auditability rather than final report content.

If the user only wants a final report and does not request WeCom collection, do not run WeCom probe/full automation and do not create WeCom diagnostic artifacts.

### 7. Artifact lifecycle and storage expectations

The skill must explain that artifacts are disk files, not memory-resident state. They can accumulate on disk if every run is kept, especially WeCom diagnostics.

Expected artifact behavior by mode:

- Skill interview / prompt-only: no files.
- Git scan without `--output`: stdout only, no files.
- Git scan with confirmed `--output`: one markdown/text evidence file per requested output.
- Final report generation: one final report file, plus any explicitly requested format copy.
- WeCom `--prompt-only`: stdout only, no files.
- WeCom `--probe-only`: diagnostic-heavy; creates screenshots, region crops, OCR text, and trace files under the confirmed `--screenshot-dir`.
- WeCom full desktop automation: diagnostic-heavy; creates a run directory with screenshots, region crops, OCR text, trace JSON/JSONL, and may also create markdown/JSON summary outputs if requested.
- WeCom `--semi-manual` / `--manual-input`: should create only the requested markdown/JSON output files, not a full screenshot/OCR diagnostic tree.

The agent must not imply that every skill invocation creates a large artifact tree. Large artifact trees are expected only for WeCom probe/full automation.

Before diagnostic-heavy WeCom runs, the agent must warn:

```text
本次企微诊断会在 [目录] 下生成一个 run 目录，包含截图、区域裁剪、OCR 文本和 trace，可能有几十个文件。它们用于诊断和验收，不是最终报告内容。验收后如不需要保留，可以删除该 run 目录。
```

Recommended retention rule:

- Keep the latest successful WeCom run and any failed run still needed for debugging.
- After acceptance, old run directories may be deleted by the user or by an explicitly requested cleanup task.
- The skill/agent must never silently delete diagnostics; cleanup requires explicit user confirmation and exact target path.

## Acceptance Criteria

- The skill clearly requires output-location confirmation before any file write.
- The skill no longer treats the current terminal project as an implicit output workspace.
- A local git repo used as evidence is not polluted with `outputs/` by default.
- Git statistics can still proceed in stdout/no-file mode when no output folder is confirmed.
- WeCom diagnostic output requires explicit safe paths before execution.
- The user is warned that WeCom diagnostics can generate screenshots, OCR text, region crops, trace JSON/JSONL, markdown, and JSON summaries.
- Normal git/report workflows do not create WeCom diagnostic artifacts.
- Diagnostic-heavy WeCom modes are clearly opt-in and write only under confirmed safe paths.
- Artifact lifecycle is documented: normal calls are file-free or low-file-count, while WeCom probe/full automation is diagnostic-heavy and old run directories are safe to delete only after explicit user confirmation.
- Installed Claude skill behavior is updated if the user tests through the installed skill.
- No full-auto WeCom live test is run without renewed supervised authorization.

## Risk Notes

- This is a safety-boundary task. Keep the change narrow.
- Avoid broad refactors that could disturb already accepted collector behavior.
- Be careful not to weaken the fast path too much: skip repeated questions when values are known, but never skip write-location confirmation.
- Do not delete the accidental files in the user's random project unless the user explicitly requests cleanup and confirms the exact path.
